Намір і критерії (1–2 речення)

Реалізовано платну бібліотеку DimPenShelf: читачі резервують книги та оплачують їх тимчасове позичання, можливе замовлення доставки.

Топ-3 розбіжності (spec ↔ артефакт) + коміт-виправлення:

1. У spec не було вказано актора "Бібліотекар". В ітерації-3 чомусь з'явився актор "Бібліотекар". Потім довелось його повністю видаляти. Коміт-виправлення: `d9d542b578183127742e360757f0bdca883cc40e`
2. Додано авторизацію як попередню умову. spec не визначав авторизацію як окремому вимогу, хоча у майже всіх сценаріях вона згадувалась; реалізація додає US-00 (Авторизацію користувача), захищаючи всі дії  Коміт-виправлення: `4ecefc87f3f3848dfed80f3f689e198806ffcf32`.
3. Змінено життєвий цикл статусу примірника книги. Початкова логіка резервування не фіксувала статус IN_USE після оплати, натомість використовувала RESERVED; Пізніша реалізація змінює статус на IN_USE після успішної оплати та забороняє бронювання, якщо статус RESERVED або IN_USE (до цього фактично можна було запронювати книжку яка вже була IN_USE). Коміт-виправлення: `4ecefc87f3f3848dfed80f3f689e198806ffcf32`.

Ключове рішення — які альтернативи зважив і чому обрав цю (ADR):

Архітектурні рішення, що лежать в основі цих відхилень, задокументовані у ADR:
- `adr/0003-reservation-ttl.md` — TTL бронювання та переходи статусу примірника (RESERVED / IN_USE / AVAILABLE). Альтернативи: періодичне-очищення, відкладені повідомлення.
- `adr/0004-time-source.md` — єдине джерело часу (UTC формат). Альтернативи: Date.now() скрізь (проблеми з часовими поясами) — відхилено.
- `0005-delivery-service-actor.md` - Служба доставки як активний зовнішній актор. Альтернативи: Служба доставки як пасивна деталь реалізації, Моделювання всіх зовнішніх сервісів як акторів.

Перевірка — узгодженість із попередньою моделлю (як перевірив):

- Пройшовся між EARS → User Story → Gherkin → UC перевірив чи всі id відповідні у tracing-matrix.md: кожен EARS ID має відповідний User Story ID, кожен User Story має принаймні три Gherkin сценарії, кожен сценарій має Use Case ID з діаграми use-case-diagram.puml.
- Перевірив статуси примірника. Щоб бронювання було дозволене лише для AVAILABLE, після оплати статус стає IN_USE.
- Актори та прецеденти з use-case-diagram.puml порівняні зі spec.md: Reader, Author, Delivery, Payment System.
- Перевірив чи точно Автор успадковує Читача.
- Перевірив чи не проігнорована EARS-11 повністю, щоб в неї був детальний опис.
- Перевірив чи повністю видалені згадки про випадкового актора "Бібліотекар"
- Перевірив чи Платіжна система тепер як функціонал, а не актор. І перевірив щоб Служба доставки була окремим актором
