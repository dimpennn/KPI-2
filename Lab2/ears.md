# EARS-вимоги (DimPenShelf)

Нижче наведено вимоги до системи, написані у форматі EARS. Кожна вимога має унікальний ідентифікатор, шаблон та однозначне тестоване формулювання.

Актори системи: `Читач`, `Автор`, `Служба доставки`.
Зовнішній сервіс (деталь реалізації): `Платіжна система`.

---

## EARS-01 — Ubiquitous
Система повинна дозволяти зареєстрованому Читачу переглядати каталог книг та перевіряти кількість і статус наявних примірників.

## EARS-02 — Ubiquitous
Система повинна дозволяти зареєстрованому Читачу бронювати видання книги, якщо статус примірника ДОСТУПНИЙ.

## EARS-03 — Event-Driven
Коли Читач підтверджує оплату бронювання і система успішно виконує авторизацію оплати через платіжний шлюз, то система повинна створити квитанцію (Receipt) з дедлайном повернення (збереженим у UTC), встановити термін дії бронювання через вбудований механізм БД (TTL) та змінити статус примірника книги на ВИДАНО (IN_USE).

## EARS-04 — Unwanted Behaviors
Якщо під час виконання системою авторизації оплати платіжний шлюз відхиляє транзакцію або відбувається скасування замовлення, то система повинна не створювати квитанцію (або ініціювати повернення коштів) та повідомити Читача про відмову в оплаті.

## EARS-05 — State-Driven
Коли примірник книги перебуває в стані РЕЗЕРВОВАНИЙ або ВИДАНО (IN_USE), то система не повинна дозволяти іншому Читачу бронювати цей примірник.

## EARS-06 — Optional Features
Де інтеграція зі Службою доставки присутня, то система повинна дозволяти Читачу розширити бронювання оформленням доставки (автоматично виконуючи системні дії обчислення ціни, терміну доставки та генерації накладної) і приймати ініційовані Службою доставки push-сповіщення про зміну статусу переміщення замовлення для відображення Читачеві.

## EARS-07 — Ubiquitous
Система повинна дозволяти Автору додавати власні книжки на сайт.

## EARS-08 — Ubiquitous
Система повинна дозволяти Автору переглядати статистику читань своїх книг.

## EARS-09 — Unwanted Behaviors
Якщо термін дії бронювання вийшов (за вбудованим механізмом БД TTL) і Читач не оплатив або не забрав примірник, то система повинна автоматично позначати примірник як ДОСТУПНИЙ та встановити статус бронювання як ПРОТЕРМОВАНИЙ, використовуючи єдине джерело часу (Clock) із збереженням у UTC.

## EARS-10 — Ubiquitous
Система повинна дозволяти Читачу залишати оцінку та текстовий відгук на прочитану книгу.

## EARS-11 — Ubiquitous (Uncovered)
Система повинна дозволяти Читачу додавати книги у особистий список "Прочитані" та список бажань.

## EARS-12 — Ubiquitous
Система повинна вимагати успішної автентифікації та авторизації користувача як попередню умову для будь-яких захищених дій системи (бронювання, оплата, оформлення доставки, отримання примірника, залишення відгуку, додавання книги, перегляд статистики); неавторизований доступ до цих дій повинен бути заборонений.

## EARS-13 — Ubiquitous
Система повинна використовувати єдиний ін'єктований інтерфейс Clock для всіх часових операцій (терміни бронювання, дедлайни повернення, статуси примірників). Час має зберігатися в UTC та відображатися у київському часі; пряме викликання Date.now() заборонено.

## EARS-14 — Ubiquitous
Система повинна дозволяти Читачу отримати заброньований примірник книги (UC-05 "Отримання примірника") виключно після успішної оплати оренди (UC-03) та встановити статус примірника як ВИДАНО (IN_USE) з дедлайном повернення.

## NFR — Нефункціональні вимоги

### NFR-01 — Демографія користувачів і пристрої
Система призначена для читачів віком 18+ років та авторів книг (видавців), які входять із території України. Підтримувані пристрої: настільні комп’ютери та ноутбуки (Windows, macOS, Linux) та мобільні пристрої (iOS, Android). Підтримувані браузери: Chrome (остання версія), Firefox (остання версія), Safari (остання версія), Edge (остання версія). Нативного мобільного додатку не передбачено.

### NFR-02 — Мова інтерфейсу
Основна мова інтерфейсу: українська. Другорядна мова: англійська (лише для навчальних цілей). Усі повідомлення користувача, мітки, підказки та документація повинні бути українською мовою.

### NFR-03 — Час відгуку (p95)
- Пошук у каталозі: p95 ≤ 500 мс при навантаженні до 100 одночасних користувачів, вимірювання протягом 5 хвилин.
- Бронювання примірника: p95 ≤ 1000 мс при навантаженні до 100 одночасних користувачів.
- Авторизація оплати через платіжний шлюз: p95 ≤ 2000 мс при навантаженні до 100 одночасних користувачів.
- Отримання примірника (UC-05): p95 ≤ 500 мс.
Міряти p95 слід за період не менше 5 хвилин стійкого навантаження на продакшн-еквіваленті середовища.

### NFR-04 — Обробка навантаження
Система повинна одночасно обслуговувати принаймні 500 користувачів. При перевищенні ліміту: зайві запити ставляться в чергу, користувачам відображається повідомлення «Система перевантажена, спробуйте пізніше», автоматичний повтор спроби через 30 секунд. Якщо черга перевищує 100 запитів, додаткові запити відхиляються з кодом HTTP 503.

### NFR-05 — Безпека оплати
- Платіжні дані не зберігаються в базі даних системи (не підпадає під вимоги PCI DSS до зберігання даних карток).
- Усі канали зв’язку з платіжним шлюзом шифруються через TLS 1.3.
- Вебхуки від зовнішніх сервісів повинні перевірятися за криптографічним підписом.
- Перед кожною оплатою обов’язкова 3D Secure автентифікація користувача.
- Максимальна сума однієї оплати: 50 000 UAH.

### NFR-06 — Доступність
Система повинна відповідати WCAG 2.1 рівню AA: підтримка скрінрідерів (NVDA, JAWS, VoiceOver), клавіатурна навігація без миші, контрастність кольорів не менше 4.5:1 для тексту, альтернативний текст для всіх зображень, підтримка масштабування шрифту до 200% без втрати функціональності.
